# Migration: the mail switches leave `services.email.enabled`

**Applies to:** every deployment that set any key under `services.email.enabled`, in any configuration source.
This includes a configuration generated by the install wizard (`bin/init.js`) with mail configured: the former wizard
wrote `enabled: { resetPassword: true, welcome: true, verifyEmail: true }` for you. `node bin/check-config.js` tells
you (see "Check before you deploy").
**Nothing to do** for a deployment that never set `services.email.enabled`, or set it to `true` or `false`.

## What changed

Until this release, `services.email.enabled` was either a boolean (the whole mail feature) or an object holding one
switch per mail (`enabled: { welcome: false, resetPassword: true, ... }`). It is now always a boolean, and each mail
has its own flat switch in `services.email`, named `send` + the former name with its first letter upper-cased:

```yaml
services:
  email:
    enabled: true                        # whole-feature switch; false: no mail of any kind
    sendWelcome: true
    sendResetPassword: true
    sendVerifyEmail: true
    # ... one sendXxx key per mail, see the table below
```

- Every `send...` switch defaults to `true`, as the former sub-keys did.
- `services.email.enabled: false` still turns every mail off, whatever the `send...` keys say.
- `services.email.enabled: true` (the default) leaves each mail to its own `send...` switch.

## Why the core refuses the former shape

A core whose configuration still holds `services.email.enabled` as an object, in **any** configuration source, does
not start. Reading the object as "on" would send again mails you switched off; ignoring a layer that holds it (because
a higher layer sets `enabled: true`) would do the same. So the boot stops and tells you what to move.

The sources checked are all of them: `override-config.yml`, a bootstrap or host file, the `config/<NODE_ENV>-config.yml`
base layer, environment variables (`services__email__enabled__welcome=false` builds the object form), command-line
arguments (`--services:email:enabled:welcome=false`), and the shipped defaults.

A switch set to something other than `true` or `false` is refused at boot as well: an empty `enabled:` left behind
after its children were commented out (YAML reads it as `null`), a quoted `'false'`, or `yes` / `no` / `on` / `off`
(strings for the YAML parser, not booleans). All of them used to count as "on", `off` included. Write the YAML
booleans `true` and `false`, in environment variables too.
Unknown `send...` names (a typo such as `sendWelcom`) are not checked.

## What the boot refusal says

One problem per configuration source that holds the object form, for example:

```
Configuration is invalid at [services:email:enabled] services.email.enabled must be true or false. The per-mail switches moved out of it, and this core does not start rather than send mails that were switched off. Found in override-file (From file: /app/config/override-config.yml):
  services.email.enabled.welcome: false  ->  services.email.sendWelcome: false
  services.email.enabled.resetPassword: true  ->  services.email.sendResetPassword: true
Move each line to its new key, then set services.email.enabled to true or remove it (false still turns every mail off).
```

- Each key found is listed with its value and its replacement. A value that is not a boolean is shown as
  `<not a boolean>`.
- A sub-key that is not one of the mails below is listed as `services.email.enabled.<key>: not a mail switch, remove it`.
- For an environment variable, both sides are written in environment form:
  `services__email__enabled__welcome=false  ->  services__email__sendWelcome=false`.

## Migrating

Move each line out of `enabled`, prefix it with `send` (first letter of the former name upper-cased), then remove
`enabled` or set it to `true`.

Before:

```yaml
services:
  email:
    enabled:
      welcome: false
      resetPassword: true
      verifyEmail: false
```

After:

```yaml
services:
  email:
    enabled: true
    sendWelcome: false
    sendResetPassword: true
    sendVerifyEmail: false
```

| Former key (under `services.email.enabled`) | New key (under `services.email`) |
|---|---|
| `welcome` | `sendWelcome` |
| `resetPassword` | `sendResetPassword` |
| `verifyEmail` | `sendVerifyEmail` |
| `mfaChange` | `sendMfaChange` |
| `externalIdReleased` | `sendExternalIdReleased` |
| `accountDeletionScheduled` | `sendAccountDeletionScheduled` |
| `accountDeletionReminder` | `sendAccountDeletionReminder` |
| `accountDeletionBlocked` | `sendAccountDeletionBlocked` |
| `accountTransferNamed` | `sendAccountTransferNamed` |
| `accountTransferClaim` | `sendAccountTransferClaim` |
| `accountTransferStarted` | `sendAccountTransferStarted` |
| `accountTransferCancelled` | `sendAccountTransferCancelled` |
| `accountTransferLapsed` | `sendAccountTransferLapsed` |
| `accountTransferCompleted` | `sendAccountTransferCompleted` |

### Environment variables

The same rule applies: `services__email__enabled__welcome=false` becomes `services__email__sendWelcome=false`, and
`services__email__enabled__resetPassword=true` becomes `services__email__sendResetPassword=true`. Remove the former
variables: one left in the environment is enough to stop the boot.

### Page URLs

`auth.passwordResetPageURL` stays required while the password-reset mail is on (`enabled` is not `false` and
`sendResetPassword` is not `false`). `auth.emailVerificationPageURL` is required at boot when you set
`services.email.sendVerifyEmail: true` yourself, as it was with the former key; left at its default, a missing page
URL keeps the verification mail off with a warning at every boot.

## Check before you deploy

`bin/check-config.js` runs the same check on your configuration file, the bootstrap file next to it, the base layer of
`NODE_ENV` and the environment, without starting a core:

```bash
node bin/check-config.js /path/to/override-config.yml
```

With the Docker image:

```bash
docker run --rm -v /host/config:/app/config pryvio/open-pryv.io check-config /app/config/override-config.yml
```

It exits non-zero and prints the same message as the boot when a former key is still there.

## Rolling back

Keep a copy of your former configuration. A release before this one does not know the `send...` keys and reads
`enabled: true` as "every mail on": rolling the image back while keeping the migrated configuration sends again every
mail you switched off, without any warning. Roll the configuration back together with the image. The two shapes cannot
live in one file: this release refuses the object form, the former releases ignore the `send...` keys.
